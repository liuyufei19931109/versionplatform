# 首版路线图

首版面向自己管理服务器、使用 Docker Compose 部署服务的团队。**以下为开发计划。** 目标是让用户带来源码或已有镜像，在首次发布前检查配置，复用制品历史、预生产验证、生产动态码和按历史制品回滚。

| 用户手里有什么 | 首版要让他做到什么 |
| --- | --- |
| Git 仓库、Dockerfile、镜像仓库、测试服务器 | 在页面选分支，从源码构建镜像，把它发到测试机，看到健康检查结果。 |
| Jenkins、GitLab CI 等系统产出的镜像 | 由人或 CI 登记镜像，让平台接手预生产和生产发布。可以完全不授予平台源码仓库权限。 |

## 实施顺序

| 顺序 | 交付内容 | 这一步完成的标志 |
| --- | --- | --- |
| 0 | 建立独立的源码和运行边界 | 开源版的开发、测试、发布都使用自己的资源。 |
| 1 | 清理默认配置，打通两种制品来源共用的发布逻辑 | 平台能区分“自己构建”和“外部登记”，并按镜像摘要部署。 |
| 2 | 功能一 · 通用 Dockerfile 服务 | 一个没有 Maven 或 npm 配置的仓库能在测试机跑起来。 |
| 3 | 功能二 · 发布已有镜像 | 外部 CI 提供的镜像能独立走完预生产、生产和回滚。 |
| 4 | 功能三 · 首次接入自检 | 第一次发版前，用户能看见哪一步可用、哪一步需要修。 |
| 5 | 打包、文档与独立安装验收 | 新用户能按公开文档跑通上面两条路径。 |

### 0. 隔离源码、凭据和运行环境

- [x] **核对源码**：已从工作区选取前端、后端、测试和运行脚本，包括未进入原提交的源码，并在临时目录重编译，与本地交付包逐项核对。
- [x] **建立独立源码仓**：仅引入白名单源码、依赖清单、脱敏测试和文档。本仓拥有独立提交历史，内部运维记录、验证输出、数据库、备份、私钥和签名文件均排除在导入范围外。
- [ ] **首次部署前**：为开源验收另行准备 Compose 项目、端口、数据卷、加密密钥、镜像命名空间和测试节点；Git、SSH、CI 及镜像仓库凭据使用专门的测试身份。本次仅使用临时构建目录及离线依赖缓存，未配置任何服务器或运行凭据。

**验收**：从空目录启动测试实例时，只会创建或访问本实例配置的资源；测试账号只能访问示例仓库、镜像与测试节点。公开源码及最终发布附件均完成敏感信息检查。

### 1. 改造公共配置与制品记录

- [ ] **改现有配置**：移除公司专用的 Git 组织、构建仓库、服务白名单条目、镜像仓库、私服地址和日志根目录默认值。允许管理员配置自己的可信仓库和日志目录，保留访问范围校验。按服务识别或指定基准分支，打包、版本管理和合回都使用同一配置。生产成功后自动合回由管理员显式启用。
- [ ] **改安全默认值**：首次安装由用户设置管理员口令，重启保留账号的停用状态。SSH 密码连接也校验可信主机指纹，指纹变化时拦截操作并提示核对。
- [ ] **改制品与发布校验**：现有制品和版本小结依赖“平台内成功的打包任务”。保留这条校验，同时给外部制品添加独立的来源记录。发版、重试、历史查询和版本小结都能识别两种来源；外部来源不得伪造成一次平台构建。
- [ ] **新增镜像摘要校验**：两条路径都记录镜像仓库、镜像名和摘要。标签供人识别，部署和回滚使用 `仓库/镜像@sha256:…` 锁定实际内容。摘要不可验证时停止发布并说明原因。已有历史记录仍可查询；再次部署旧记录前须能核实当时的摘要。

**验收**：只有 `main` 的仓库可通过基线检查；空配置不会访问内部资源；同一标签改指新镜像后，选原制品部署或回滚仍拉取原摘要。

### 2. 功能一 · 通用 Dockerfile 服务

| 改造项 | 清单 |
| --- | --- |
| 改现有 | 把目前主要挂在“前端服务”下的仓库 Dockerfile 模式提取为独立构建方式。复用 Git 拉取、提交锁定、Docker 构建与推送、任务日志和发布向导。现有 Java、静态前端等构建方式仍按各自配置执行。 |
| 新增 | 新建服务时可选“从 Dockerfile 构建”，填写仓库、分支、构建上下文、Dockerfile 路径、目标镜像仓库，并配置部署端口及健康检查地址。校验路径位于检出的仓库内。 |
| 首版边界 | 支持受信源码仓库和本机 Docker 构建，发布到 SSH 可达的 Linux/Compose 目标。业务语言工具链由 Dockerfile 定义。 |

- [ ] **验收**：准备一个只有 `main` 分支的小型 Go 或 Python 服务，健康检查路径为 `/healthz`。构建机只为该业务提供 Git 和 Docker，从选定提交构建并推送镜像后，目标机能拉取、启动并通过健康检查。错误的 Dockerfile 路径应在构建前被指出。

### 3. 功能二 · 发布已有镜像

| 改造项 | 清单 |
| --- | --- |
| 改现有 | 制品列表和发版向导展示制品来源、镜像摘要及来源记录。预生产验证、生产动态码、逐节点健康检查、历史和回滚覆盖外部镜像。Git 基线与合回只适用于有对应源码校验记录的流程。 |
| 新增 | 提供“登记已有镜像”页面和 CI 登记 API。记录所属服务、镜像与摘要、来源提交、流水线地址或人工来源说明，以及登记身份与时间。外部提交号标明由登记方提供。 |
| 权限与重试 | CI 凭据只可为指定服务和允许的镜像仓库登记制品。登记与发布分开授权。重复提交同一请求只生成一条记录；同一请求标识搭配不同内容时返回冲突。 |
| 首版边界 | 已有镜像可以直接进入独立服务的发布流程，无需 Git 账号。版本小结能引用已关联的外部制品；无源码场景下创建跨仓版本计划留到后续。 |

- [ ] **验收**：不给平台 Git 凭据，用 CI 连续两次登记同一请求，制品列表只有一条记录。越权登记被拒，直接发生产被拦；预生产健康检查通过后，授权用户以动态码确认生产发布。全程可追溯到来源流水线，且不会触发 Git 合回。

### 4. 功能三 · 首次接入自检

现有服务器页已经能测 SSH 和 Compose，发布向导也有选包后的预检。新增的入口放在**服务配置页**，保存配置后就能用，尚无制品也能检查。先选择接入方式，再决定检查项。

| 检查位置 | 从 Dockerfile 构建 | 发布已有镜像 |
| --- | --- | --- |
| 源码与构建机 | 检查 Git 读取、基准分支、Dockerfile 与上下文、Docker 引擎可用性 | 跳过源码和构建机检查 |
| 镜像仓库 | 检查地址、认证及能验证的权限。首次真实推送成功前，推送能力显示“待实测” | 校验指定镜像摘要能否读取，区分镜像不存在与凭据拒绝访问 |
| 部署目标 | 核对 SSH 指纹和认证、Compose 目录与服务名、健康检查配置；区分平台端和目标机的镜像访问能力 | 同左 |

- [ ] **改现有**：提取现有分支读取、SSH 和 Compose 检查供两处复用。保留任务提交时对制品及生产准入的再次校验。
- [ ] **新增**：按检查项展示“通过 / 失败 / 待实测 / 跳过”、原因、修改入口和重试操作。检查过程不推送镜像、不启动容器、不变更目标环境，输出隐藏凭据。
- [ ] **验收**：分别制造分支不存在、镜像认证失败、Compose 服务名写错三种问题，都能定位到对应配置；已有镜像模式下缺少 Git 凭据仍可继续。

### 5. 开源交付与放行

- [ ] 提供平台自身的 Compose 安装文件、`.env.example`、首次管理员设置、持久化目录和备份恢复说明。区分“安装平台的机器”“执行构建的机器”和“部署业务的目标机”。
- [ ] 附一个最小 Dockerfile 示例服务、一份可复制的 CI 镜像登记示例，以及使用独立测试节点的部署说明。所有样例使用公开或本地测试资源。
- [ ] 公开前确定许可证，核对第三方代码和素材的再分发条件，附上许可证文件和问题反馈入口。
- [ ] 请一位未参与开发的人在空环境按文档分别完成两条路径。再部署第二个版本，并从发布历史回滚到上个摘要。核对运行结果、操作记录与来源一致，再发布首个公开版本。

## 首版止于哪里

本轮只新增上述三个产品功能。已有发版能力按所依赖的模块复用和回归。按服务和环境细分人员授权、可分享的服务模板、自定义流水线编排、Kubernetes、多租户以及更多云构建或移动分发适配均留待后续。这里列出的 CI 登记权限属于“发布已有镜像”的必要条件，随首版交付。
